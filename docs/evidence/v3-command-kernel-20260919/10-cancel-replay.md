# 10 — Cancel and replay

Cancel (`POST …/cancel`, platform.command, expected_version + reason, Idempotency-Key): persisted/queued → cancelled, whether or not a worker holds the outbox lease (the command row lock is the dispatch boundary: queued → dispatching refuses a cancelled command, so no attempt can open after the cancel commits); dispatching/accepted/readback_pending → reconciliation_required with `cancellation_reason` set and `cancelled_at` NULL (never pretend); terminal → 409; repeated request with the same key → the original response; stale version → 409. Unleased outbox intents of a cancelled operation are cancelled and never claimed; a leased intent is closed by its owner (the bus returns outcome `cancelled`). A cancel that lands after the attempt opened but before the provider call dead-letters the operation (`cancel_requested_provider_missing`, error_class `cancelled_before_send`; nothing was sent). A standing cancel request is honoured by the reconciler: provider NOT_FOUND dead-letters with `cancel_requested_provider_missing` (outcome unknown) instead of re-queueing; MATCHED still completes (the cancel came too late). A provider acknowledgement after a cancel keeps its `provider_operation_id` for the read-back. The operator `POST /v1/outbox/{id}/cancel` refuses command intents (409): cancel the operation instead.

Retry (`POST …/retry`): failed → queued only. Refused (409) while a cancel request stands, and for adapter commands unless the owning adapter advertises `safe_reexecution` (the compatibility route, which has no registry, is always refused for adapter commands). For a non-reexecutable adapter the recovery path is REEXECUTE.

Replay (`POST …/replay`, platform.command.replay + realm role platform-operator, enforced by Middleware from the verified token): REPROCESS = the ledger's reconcile mutation (readback-only, no new effect; only for unknown-outcome states); REEXECUTE = a new governed operation (new command id, new idempotency key required, fresh policy + safety, adapter must advertise safe_reexecution, except the waiver below) allowed only from failed/dead_lettered/cancelled; an operation in reconciliation_required is refused ("reconcile first"). Replay linkage (`replay_mode`, `replay_of`) in the new operation's first audit row.

REEXECUTE waiver (non-reexecutable adapters): allowed only for a dead-lettered operation whose dead-letter record proves no provider request exists (`app/platform/outcome_codes.py:proven_not_sent`): `attempt_number == 0` with `effect_gate_denied`, `deferral_exhausted`, `dispatch_age_exceeded` or `terminal_failure`, or the bus's pre-send cancel (`cancel_requested_provider_missing` with error_class `cancelled_before_send`) on `attempt_number == 1` only (a pre-send cancel on a later attempt cannot prove the earlier attempts sent nothing), and no later attempt. Poisoned dead letters are never waived. Operator role and a new idempotency key are still required.

Deferral budget (interim until the C1 deferral counter): a known-safe deferral (readiness, transient safety denial, open circuit, full bulkhead) on the final outbox attempt dead-letters the command first (`deferral_exhausted` at attempt 0, else `retry_exhausted`), then the worker dead-letters the intent, so the command never stays active behind a dead outbox row. Fail-closed: the command is terminalized only when a fresh re-read shows it persisted or queued and its audit history never entered accepted, readback_pending, reconciliation_required or completed; a command that was ever in one of those states (for example re-queued after reconciliation) is not dead-lettered "without a provider effect" and is left for reconciliation.
